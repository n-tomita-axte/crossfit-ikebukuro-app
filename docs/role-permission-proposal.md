# 役割と操作権限の分離 ― 設計案

## 背景・課題

現状の`profiles.role`は、`member` / `coach` / `admin`の3値で、
「会員から見てどう見えるか（立場・表示）」と「何を操作できるか（権限）」の
両方を1つの列で兼ねています。

打ち合わせで出ていた懸念点はこの通りです。

> コーチをそのまま管理者権限に上げてしまうと、コーチという立場ではなくなってしまう。
> 例えば今後、コーチがメンバーにコメントを入れるような機能を作る場合、
> 管理者に上げた瞬間にコーチ表記でコメントできなくなるのはおかしい。
> 立場（役割）と操作権限は分けて考える必要がある。

つまり、**「コーチとして表示・機能を保ったまま、管理者相当の操作もできる人」**を
作れない、というのが今の設計の限界です。今は`role`を1つ上げ下げするだけの
実装（`admin_set_role`関数）なので、「コーチ」と「管理者権限を持つコーチ」を
両立できません。

## 設計案

検討した2つの方向性を、トレードオフとあわせて示します。

### 案A: 権限フラグを追加する（変更が小さい）

- `profiles.role`は今まで通り`member` / `coach`の**表示用の立場**として残す
  （`admin`という値はロールから外し、後述の権限フラグに置き換える）
- 新しい列`profiles.can_manage boolean not null default false`を追加し、
  「管理操作（役割変更など）を行えるか」を独立して持たせる
- `is_admin()`関数の中身を「`role = 'admin'`」から「`can_manage = true`」に変更するだけで、
  既存のRLSポリシー・画面コードはほぼそのまま使える
- 例: 「表示上はコーチ、かつ管理操作もできる人」→ `role = 'coach'`, `can_manage = true`

**メリット**: 変更範囲が小さく、今回のご要望（コーチ表示を保ったまま管理操作を付与）に
必要十分な対応ができる。移行も1回のマイグレーションで完結する。

**デメリット**: 権限の種類が今後増えていくと（例:「WODは編集できるがコメントは消せない」
のような細かい制御をしたくなった場合）、列を追加し続けることになり、
組み合わせが増えるたびにコードの分岐も増えていく。

### 案B: 権限テーブルとして切り出す（将来の拡張を見込む）

- `profiles.role`は`member` / `coach`の2値の**表示用の立場**に簡素化
- 新しく`permissions`テーブルを作り、「誰が」「何をできるか」を行として持つ
  ```sql
  create table public.permissions (
    user_id uuid references public.profiles(id) on delete cascade,
    permission_key text not null, -- 'manage_roles' / 'manage_workouts' / 'moderate_comments' など
    granted_by uuid references public.profiles(id),
    granted_at timestamptz not null default now(),
    primary key (user_id, permission_key)
  );
  ```
- `has_permission(key text) returns boolean`のようなSQL関数を用意し、
  RLSポリシーや画面から呼び出す
- 例: 「表示上はコーチ、かつ役割変更もできる人」→ `role = 'coach'` +
  `permissions`に`('その人のid', 'manage_roles')`の行を追加

**メリット**: 将来「コメント機能」のように新しい操作単位の権限が増えても、
テーブル構造を変えずに行を追加するだけで対応できる。「役割変更はできるが
WOD削除はできない」のような、権限ごとの細かい制御もしやすい。

**デメリット**: 案Aよりテーブル設計・移行・管理画面の作り直しのコストが大きい。
権限の種類（`permission_key`）が増えるたびに、それぞれの意味をコード側で
把握しておく必要がある。

## 推奨

今回いただいているご要望（コーチ表示を保ったまま管理操作を付与したい）だけであれば、
**案A**で十分に対応できます。変更も小さく、今のRLS設計をほぼ壊しません。

一方、「今後のコメント機能」のように、今後も権限の種類が段階的に増えていくことが
見込まれているのであれば、最初から**案B**にしておいた方が、将来作り直す手戻りが
少なくなります。コメント機能の要件が具体的になった時点で改めて相談し、
その時点で必要な権限の種類（コメントの投稿/編集/削除など）を洗い出してから
判断するのも一案です。

## 移行時に検討が必要な点（どちらの案でも共通）

- 既存の`role_changes`監査ログとの関係
  - 案A: `role`の変更と`can_manage`の変更、両方を監査ログに残すか
  - 案B: `permissions`の付与・剥奪も監査ログの対象にするか（`permission_changes`テーブルを別途作るか）
- 既存の`role = 'admin'`のユーザーをどう移行するか
  - 案A: `role`を`coach`または`member`に付け直した上で`can_manage = true`にする
  - 案B: 同様に`role`を付け直した上で、`permissions`に`manage_roles`などの行を追加する
- `admin_set_role`関数の扱い
  - 権限付与専用の新しい関数（例: `admin_grant_permission`）を用意するか、既存関数を拡張するか
- 画面側の変更
  - `/admin`の役割変更画面を、「立場（role）」と「権限（can_manage or permissions）」を
    別々に操作できるUIに変更する必要があります
